# 개발

[English](/operations/development).

독립 PHP 검사 도구는 설치한 `var/tools/bin/php` 래퍼를 사용하고 릴리즈를 `config/toolchain.json`과 비교하며 들어온 셸 경로에서 PHP를 선택하지 않는다. PHP 확장 생성/빌드·네이티브 테스트는 같은 설치 도구 세트를 사용한다. 다른 시스템 PHP에 대한 셸 조회는 이 target이 사용한 인터프리터의 증거가 아니다.

PHP 라이브러리 요구사항은 `>=8.4`(`>=8.4.0`과 동등)로 유지한다. 개발/검증 기준은 PHP `8.4.27`이며 Windows 설치 기준은 `8.4.27-1`이다. 개발 patch를 올려도 라이브러리의 최소 지원 버전을 올리지 않는다.

단계 분리 이전에는 parity job이 script 단위 테스트 job과 독립적으로 `parity-check`를 실행했다. 둘은 각 checkout에 고정 의존성을 설치했으며 `ci-passed`는 둘 다 요구했다. 모든 suite target은 여전히 정확히 한 번 실행된다. CI의 setup-node cache 조회, bootstrap과 이후 npm 설치는 `var/bootstrap/npm-cache`를 사용한다. cache는 설치 패키지나 빌드 출력이 아닌 다운로드만 저장하며 package lock이 기준이다. CI 40439038565에서 scripts는 7분 04초 대기 후 12분 23초 실행됐고, script 단위 테스트 230.7초와 parity 240.1초가 순차 실행됐다. target을 분리해 이 순서를 제거하며, 새 실행에서 결과 시간과 대기 시간을 따로 측정해야 한다.

86edcaa1의 CI 40450000056은 모든 worker와 ci-passed를 통과했다. 첫 worker 시작부터 집계 완료까지 8분 06초, 대기 8초로 전체 8분 14초다. scripts 5분 47초와 parity 6분 55초가 독립 실행됐고 가장 긴 worker는 showcase의 7분 24초다. 네트워크·설치 시간은 실행마다 달라 이 값은 관측 결과이며 고정된 단축 시간을 뜻하지 않는다.

언어별 의존성 설치 분리 후 c634ec15의 CI [40671820218](https://github.com/polyspec/template/actions/runs/40671820218)은 모든 worker와 ci-passed를 통과했다. gates 40671820222와 갱신된 그래프의 의존성 검토 40670361859도 통과했다. parity는 바인딩 253개를 두 번 실행해 5,622개 케이스를 통과했다. 실행은 10분 04초, 대기 4초로 전체 10분 08초이며 가장 긴 worker는 PHP의 9분 20초다. 분리한 의존성 단계는 npm 전용 0초, Go·Python 1초, PHP 3초인 반면 전체 도구 단계는 여전히 64–69초이며 parity 의존성 단계는 7초다. 네트워크·bootstrap과 테스트 시간은 실행마다 달라 전체 시간 단축을 입증하지 않는다. T27.1-9-1은 공급자 릴리즈 후에만 선택 설치를 연동한다.

Kit은 고정 도구 선택 설치를 제공한다. 네이티브 CI worker는 `make install-tools TOOLS="..."`로 필요한 도구를 선언한 뒤 자체 잠금 패키지 그래프를 설치한다. PHP 확장 worker는 `make kit-install-php-arginfo`와 `make kit-install-symbols EXTRACTORS=php`도 사용하며 템플릿에 설치 코드를 복사하지 않는다. 복합 스크립트·생성·구분자·showcase worker는 실행에 필요한 전체 환경을 유지하고 toolchain 감사는 선언된 전체 도구를 검증한다. Pages는 Node만 준비한다. 설치는 온라인이고 검사는 오프라인이다.

Kit은 독립적인 `parity-api-check`와 구현별 `parity-bindings-<implementation>-check` 여섯 개를 소유한다. `.github/workflows/ci.yml`의 job `kit`이 호출하는 kit pipeline `.github/workflows/ci-pipeline.yml`의 job `parity-api`와 `parity-bindings`가 각각 정확히 한 번 실행하고, `.github/workflows/ci.yml`의 다른 어떤 job도 그것을 실행하지 않는다(T27.1-44, T27.1-43). 템플릿은 공급자의 recipe를 교체하지 않고 빌드 선행 조건만 제공한다. `config/ci.json`은 동기화한 kit pipeline의 단계 모드와 네이티브 패키지 준비를 선언하며, Kit이 전체 범위를 검증하고 그 parity setup이 `packages/php-ext`의 arginfo 생성기를 직접 설치한다. 기본 `parity-check`는 공급자의 전체 검사로 유지한다.

공유 도구는 lock으로 고정한 npm package `@polyspec/kit`에서 온다. 깨끗한 checkout은 먼저 `devEngines`의 npm을 checkout 밖에서 실행해 lock을 설치한다. 기계의 npm은 `devEngines`가 다른 npm을 이름하는 폴더에서 실행을 거부하기 때문이다(`npm exec --package=npm@<version> -- npm --prefix <checkout> ci --ignore-scripts --allow-remote=root`, kit K938). CI도 첫 make 전에 이 방식으로 설치한 package를 준비한다. Makefile은 `node_modules/@polyspec/kit/scripts/kit/kit-bootstrap.mk`를 include하며 bootstrap은 native 개발 link에서는 source 도구를, release package에서는 컴파일한 도구를 선택한다. 형제 checkout은 필요하지 않다. `make install-tools TOOLS=npm`은 설치한 package의 bootstrap installer를 실행하고 `var/tools/bin`에 npm wrapper를 쓰며, `make install-packages`는 고정한 npm으로 `package-lock.json`을 설치한다. `make install-tools TOOLS=npm`은 machine의 아무 node로 시작해 `config/toolchain.json`의 `mise` sha256으로 확인한 release archive에서 mise를 설치하고, 그 mise로 `mise.toml`의 node를 설치하며, npm wrapper는 그 node로 npm을 실행한다. 이후의 모든 단계는 checkout의 node를 실행한다(kit K171). 그 뒤 `make install`은 `make install-tools`(`$(KIT)/install-tools.$(KIT_EXT)`)를 실행하며, 이것은 `mise.toml`의 모든 도구를 `mise install --locked`로 `mise.lock`의 digest에 맞춰 `var/tools/mise`에 설치한 다음 kit의 PHP lint를 설치한다. 도구 이름은 받지 않는다. `mise.toml`을 바꾼 뒤에는 `make toolchain-lock`이 linux-x64, linux-arm64, macos-arm64, macos-x64의 `mise.lock`을 쓴다. recipe는 machine의 Go와 Python을 실행하지 않고, machine의 npm, Go, Python은 바꾸지 않는다. kit의 kit.mk는 모든 recipe를 checkout의 mise 환경으로 실행하고 `var/tools/bin`과 mise의 shim인 `var/tools/mise/shims`를 `PATH`의 맨 앞에 둔다. bootstrap은 `var/tools/go.mod`를 쓰므로 `var/tools` 아래의 Go 소스는 `./...`가 순회하지 않는 별도 module이다(kit K135). Makefile은 `GOTOOLCHAIN=local`을 export하므로 go는 다른 toolchain을 내려받지 않고, `GOCACHE=var/go/cache`를 export하므로 go는 다른 checkout이나 실행과 함께 쓰는 cache가 아니라 checkout의 build cache에 build한다. GNU Make 3.81은 shell 문법이 없는 recipe 줄을 직접 시작하고, `SHELL`이 다른 shell을 가리켜도 export된 `PATH`가 아니라 make가 시작할 때의 `PATH`로 program을 찾는다. 그래서 recipe는 checkout의 각 도구를 절대 경로로 시작한다. node는 kit.mk의 `$(NODE)`, npm은 `$(NPM)`, go는 그 shim인 `$(GO)`로 시작하고, gofmt는 shell 문법이 있는 줄에서만 시작하며, shell은 export된 `PATH`로 그것을 찾는다. `make kit-check`는 checkout의 도구를 맨 이름으로 시작하는 recipe를 실패시킨다(kit K171). `make owner-check`가 모든 변경에 실행하는 `tests/scripts/toolchain-files.test.mts`는 recipe의 Node.js, npm, Go, Rust, PHP minor version, Composer가 이 파일들과 다르면 기대값과 실제값을 적어 실패한다. 없는 도구는 그것을 실행하는 target을 실패시킨다.

PHP는 minor version으로 고정한다. CI에서 PHP를 설치하는 setup-php는 minor version의 최신 patch를 설치하고 patch를 고정할 수 없다. `make ci-targets`의 각 실행은 자기가 실행된 version을 PHP patch까지 report의 `record.json`과 `summary.md`에 기록하고 모든 CI job이 그 report를 upload한다. Composer는 `mise.toml`에서 정확히 고정하고, setup-php는 도구를 설치하지 않는다(workflow의 `tools: none`). make는 고정하지 않는다. Makefile은 GNU Make 3.81보다 새로운 구문을 쓰지 않고, make 3.81과 GNU Make 4.4.1은 모든 target에 같은 명령을 출력했다(T17.1-4). CI job은 `ubuntu-24.04`에서 실행되고, 모든 action을 commit으로 고정하며, `make install-tools TOOLS=npm`, `make install-packages`, `make install`로 설치한다. 어떤 job도 자기 Go나 Python을 설정하지 않는다.

PHP 확장 `packages/php-ext`는 C 구현이다. kit의 `make build-php-ext`는 `config/toolchain.json`의 모든 PHP version에서 `PATH`의 php-config로 phpize, configure, make를 실행해 빌드한다. 이 php-config는 test를 실행하는 `PATH`의 php와 같은 PHP여야 하며, CI는 둘 다 setup-php로 설치한다. `make php-ext-arginfo`는 PHP build의 gen_stub.php로 stub에서 arginfo header를 만든다.

## 명령

```sh
make install
make help
make owner-check
```

`make owner-check`는 바뀐 경로의 owner check를 실행한다. 경로는 commit하지 않은 변경, `PATHS`의 경로, 또는 `BASE` 이후 바뀐 경로다. `config/owner-checks.json`은 경로 glob마다 그것을 소유하는 make target과 node test file, 그리고 모든 변경에 실행하는 test(`always`)를 선언한다. script는 같은 파일의 `inputs`는 검사 target마다 그것이 읽는 경로의 glob을 선언한다. 예를 들어 `lint-go`는 `packages/go/**`를, `conformance-generated-go`는 `packages/compiler/**`를 읽는다. input의 모든 경로에는 그 target이나 그것을 prerequisite로 실행하는 target을 선택하는 규칙이 있어야 하므로, 경로를 바꾸면 그것을 읽는 모든 검사가 실행된다. 어떤 owner보다 먼저, 어느 규칙도 소유하지 않는 tracked 경로, 규칙이 그 target을 선택하지 않는 input 경로, 아무 경로에도 맞지 않는 glob, Makefile에 없는 target, 전체 suite를 실행하는 target에서 실패하고, 각 실패는 그 경로, glob, target을 적는다. `variable`이 있는 규칙은 바뀐 경로를 target에 넘긴다. `tests/cases` 아래 변경은 `make conformance-cases CASES="<paths>"`를 실행하고, 이 target은 그 case에 대해서만 AST conformance와 생성 conformance runner 넷을 실행한다. `make check`의 conformance target들은 모든 case를 실행한다.

`make install`은 `rust-toolchain.toml`이 지정한 Rust toolchain도 `rustup toolchain install --no-self-update`로 설치하고 이미 설치되어 있으면 아무것도 바꾸지 않는 `make install-tools`(kit K151)와, 모든 `Cargo.lock`의 crate를 내려받는 `make cargo-downloads-fetch`를 실행한다. Makefile은 `RUSTUP_AUTO_INSTALL=0`을 export하고 CI workflow도 이를 설정하므로 rustup은 첫 cargo에서 toolchain을 설치하지 않는다. 한 `node --test` 실행의 test file들이 cargo를 동시에 시작했고, 그 동시 설치가 서로를 깨뜨렸다(T18.7-1). toolchain이 없으면 rustup이 `rustup toolchain install`을 적은 `toolchain '...' is not installed` 메시지로 실패한다. root `package.json`은 `packages/`의 JavaScript package를 npm workspace로 선언하고 root가 실행하는 개발 도구를 가지며, 한 package만 쓰는 도구, 곧 `packages/codemirror`의 CodeMirror peer와 `make vscode-package`가 실행하는 script `package:vsix`의 vsce는 그 package가 가진다. npm은 각 workspace package를 `node_modules`에, package의 명령을 `node_modules/.bin`에 link하며, recipe는 TypeScript, tsup, esbuild, Vitest, Playwright, VitePress, vsce를 거기서 실행한다(script는 `scripts/tools.mts`). 그래서 package는 다른 package의 build를 build가 쓰는 곳에서 읽는다(T24.2). `make install`은 `mise.toml`의 python으로 `pip download --require-hashes`를 실행하며, 이것은 `packages/python/build-requirements.txt`가 version과 SHA-256으로 고정한 build requirement를 `var/python/wheelhouse`에 내려받고, package install check는 이 directory로 Python wheel을 offline build한다.

`make build-ts`, `make template-build-language`, `make template-build-lsp`, `make template-build-codemirror`, `make template-build-vscode`는 `scripts/build-package.mts --package <package>`를 실행한다. 이 script는 입력의 hash가 `packages/<package>/dist.inputs.json`에 기록된 hash와 다를 때만 package를 빌드하고, 같으면 `dist`가 최신이라고 출력하므로 suite 한 번의 실행은 package마다 많아야 한 번 빌드한다. 입력은 package의 소스와 설정, manifest, root `package-lock.json`, package가 의존하는 이 저장소 package의 설치된 사본, Node.js version이다. TypeScript package는 tsup이 module을 묶고, TypeScript compiler가 declaration을 같은 directory에 쓴다(`template-ts`는 `tsconfig.json`과 `tsconfig.node.json`, 다른 package는 `tsconfig.build.json`으로 `tsc --emitDeclarationOnly`). declaration은 소스 file마다 하나씩 소스의 directory 구조를 따라 생긴다. tsup의 declaration 빌드는 TypeScript 7에 없는 compiler의 JavaScript API를 호출한다. 빌드는 `packages/<package>/dist.next-<pid>`에 쓰고 각 file을 rename으로 `dist`에 옮기되 file은 그것이 import하는 상대 module 뒤에 옮기므로 entry가 마지막에 옮겨지고, 그 뒤 새 빌드에 없는 이전 빌드의 file을 지운다. package를 복사하는 다른 저장소나 실행의 다음 target 같은 `dist`의 reader는 빠진 file을 보지 않는다. 한계: 바뀐 소스의 빌드가 내보내는 동안 여러 file을 읽는 reader는 두 빌드의 file을 섞어 읽을 수 있다. 예를 들어 새 빌드가 지운 chunk를 쓰는 이전 빌드의 entry다. 입력이 같은 다시 빌드는 같은 file을 쓴다. `--install`이면 `node_modules`의 npm 사본은 그 file이 package와 다를 때만 같은 방식으로 다시 설치한다. 다른 file마다 `node_modules/<name>.next-<pid>`에 쓰고 rename으로 사본에 옮기되 file은 그것이 import하는 상대 module 뒤에, `package.json`은 마지막에 옮기며, 그 뒤 package에 더는 없는 file을 지운다. 그래서 같은 `node --test` 실행의 다른 test file 같은 사본의 reader는 빠진 file을 보지 않는다. package 의존성의 변경은 `package-lock.json`의 변경이므로, 그때 설치는 실패하고 고치는 방법으로 `npm install`을 적는다. `tests/scripts/build-package.test.mts`는 자기가 의존하는 package를 직접 빌드하고 설치하므로 아무것도 빌드하지 않은 checkout에서도 통과한다.

prerequisite로 적고, Makefile은 `MAKEFLAGS += -k`를 설정하므로 make는 실패한 검사 뒤의 모든 검사를 실행하고 끝에서 실패한다. 실패한 prerequisite는 그것에 의존하는 target을 실행하지 않게 한다. 언어마다 검사하는 script(`scripts/check-generated-*.mjs`, `scripts/check-typed-generator.mts`, `scripts/check-package-installs.mts`)는 `scripts/language-checks.mts`의 `checkLanguages`로 모든 언어를 실행하고 실패한 언어를 모두 밝힌다. `tests/scripts/failure-accumulation.test.mts`가 이 규칙을 검사한다. `lint`는 kit이 복사하는 설정으로 kit의 lint target을 실행한다(T24.6). `lint-ts`는 oxlint-tsgolint와 함께 oxlint(`.oxlintrc.json`)와 knip(`knip.json`)을, `lint-go`는 각 Go module에서 golangci-lint(`.golangci.yml`)와 deadcode를, `lint-rust`는 각 Cargo workspace에서 clippy를, `lint-php`는 phpcs(`phpcs.xml.dist`)와 PHPStan(`phpstan.dist.neon`)을, `lint-python`은 ruff(`ruff.toml`)와 vulture를 실행한다. template의 format check는 `template-lint-go-format`(gofmt), `template-lint-rust-format`과 `template-lint-showcase-format`(`cargo fmt --check`), `template-lint-php-format`(Pint)이며, `template-lint-showcase-warnings`는 Rust showcase adapter를 경고를 오류로 처리해 컴파일한다. `test-rust`와 `template-test-ext`는 Rust 크레이트와 PHP 확장에 경고를 오류로 처리하는 clippy를 실행한다.

개발에서는 unit test만 실행하고, 개발 중에도 commit이나 push 전에도 전체 검사나 end-to-end 검사를 로컬에서 실행하지 않는다. `make owner-check`, conformance runner, browser test, VS Code integration test는 로컬에서 실행하지 않고, CI가 전체 suite를 실행한다. CI workflow(`.github/workflows/ci.yml`)는 `main`에 대한 push와 수동 실행(`workflow_dispatch`)마다 실행된다. 각 job은 `make ci-targets`로 자기 target을 실행하고, `CHECK_TARGETS`의 모든 target은 정확히 한 job에서 실행되며(`tests/scripts/suite-parity.test.mts`), 모든 job은 log, 실패, toolchain version의 report(`var/report`)를 upload한다.

모든 make 실행은 `core.hooksPath`를 `config/checklist.json`의 추적되는 hook 디렉터리 `.githooks`로 설정한다. `make hooks`는 이를 설정하고 hook을 쓰며 검사하고, `make hooks-check`는 `core.hooksPath`가 `.githooks`가 아니거나 hook이 없거나 실행 파일이 아니거나 바뀌었을 때 실패한다. push는 검사하지 않는다. message 규칙은 commit에서 실행되고, commit의 CI 실행은 release에서 읽는다.

버전 0.x는 `main`에서 바로 작업한다(AGENTS). pull request, merge queue, GitHub ruleset은 없다. checklist 행은 소유 unit test가 통과하면 `[o]`가 되고, `main`은 모든 행이 `[o]`일 때 한 번 push한다. 그 push에서 `.github/workflows/ci.yml`의 실행이 그 commit의 증거이다. 마지막 job `ci-passed`는 workflow의 다른 모든 job을 need로 가지고, 그중 하나가 실패하거나 skip되거나 취소되어도 그 모든 job 뒤에 실행되며(<code v-pre>if: ${{ always() }}</code>), <code v-pre>make ci-passed RESULTS='${{ toJSON(needs) }}'</code>(`node_modules/@polyspec/kit/scripts/kit/ci-passed.mts`)를 실행한다. 이 명령은 need로 가진 모든 job의 결과를 출력하고, 하나라도 `success`가 아니면 실패한다. skip된 step은 check를 통과시키므로 그 step에는 조건이 없다. `ci.yml`에 추가한 job은 `needs`에 넣으며, `tests/scripts/toolchain-files.test.mts`는 `ci-passed`가 없거나, 마지막 job이 아니거나, <code v-pre>if: ${{ always() }}</code>가 없거나, 다른 모든 job을 need로 가지지 않거나, 다른 runner에서 실행되거나, 다른 step을 실행하면 실패한다(T22.1-3). 더 새로운 push는 이전 push의 실행을 취소하지 않는다. workflow `.github/workflows/pages.yml`은 `main`에 대한 모든 push의 문서 site를 게시하고 수동 실행(`workflow_dispatch`)에서도 게시한다. `.github/workflows/release.yml`은 메인테이너가 성공한 `ci.yml` 실행의 id와 버전으로 dispatch할 때만 실행되어 그 실행의 commit을 릴리스한다(`docs/operations/publication.md`).

`test-go`, `test-rust`, `test-php`, `template-test-ext`는 `go test`, `cargo test`, PHPUnit을 `node_modules/@polyspec/kit/scripts/kit/run-tests.mts`로 실행하며, `template-test-ext`는 build된 extension을 PHPUnit의 PHP에 로드하는 `--php-extension`을 쓴다. `test-ts`, `template-test-language`, `template-test-lsp`, `template-test-codemirror`는 vitest를, `template-test-vscode`는 `node --test`를 이 runner로 실행한다. runner는 각 test가 시작할 때, 실행 중에는 5 s마다, 통과·실패·건너뜀으로 끝날 때 경과 시간과 함께 출력하고, test가 자기 timeout(30 s, `--timeout <seconds>`)을 넘으면 도구를 멈춘다. package, 파일, 실행 전체에는 시간 제한이 없다. `cargo test`는 test를 하나씩 실행하므로 각 test는 결과 전에 시작을 출력한다. PHPUnit도 10 s가 지난 test를 멈춘다(`enforceTimeLimit`, `failOnRisky`). build되지 않는 Go package는 compiler 출력과 `✖ build of <package> failed`를 출력하고, 요약 줄은 compiler error를 밝힌다. test가 하나도 실행되지 않은 실행은 `no test ran`으로 실패한다. test는 필요한 것이 build되지 않았을 때 자기를 건너뛰지 않고 그것을 build하며, conformance runner는 `--langs`가 언어를 지정하지 않으면 모든 언어를 실행하고 없는 package에서 실패한다. `template-test-scripts`는 `tests/scripts/`에 있는 runner의 test를 실행한다.

언어별 명령:

```sh
make test-ts
make test-go
make test-rust
make test-php
node tests/runner/conformance.mts --langs ts,go
make parity-check
```

## 변경 절차

1. `docs/spec/`의 명세와 `.ko.md` 파일을 수정한다.
2. `tests/cases/`의 픽스처 케이스와 `tests/fixtures/expr/`의 표현식 픽스처를 추가하거나 수정한다.
3. 패키지에 실패 테스트를 추가하고, 코드를 수정하고, 테스트를 유지한다.
4. `docs/features.md`, `docs/features.ko.md`, `CHANGELOG.md`, `CHANGELOG.ko.md`를 갱신한다.
5. 변경을 소유한 Red와 Green test와 `make docs-check`를 실행한다.
6. 동작, 주체, 대상을 명시한 메시지로 커밋한다.

`config/parity.json`의 구현별 API binding은 scalar `symbol` 또는 비어 있지 않은 고유 `symbols` 목록을 사용한다. 목록은 engine 타입·생성자·소유 program처럼 같은 검증된 계약의 정확한 공개 지점을 명명한다. Prefix·wildcard 확장은 사용하지 않는다. 선언 gate가 잘못된 binding을 거부하고 네이티브 SDK consumer 단위 검사가 목록의 모든 이름을 검증한다. 기존 연산·필드 단위 검사는 `packages/compiler/interface.json`의 canonical 공개 지점 검사를 유지한다.

공급자 공통 게이트는 Python 소스를 파싱하는 test-marker 검사를 위해 `config/ci.json`의 `tools.shared`에 Python을 선언한다. 이는 네이티브 런타임 worker와 별개로 공통 정적 검사에 필요한 도구다.
