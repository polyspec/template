# Development

[한국어](/ko/operations/development).

Standalone PHP inspection tools use the installed `var/tools/bin/php` wrapper and verify its release against `config/toolchain.json`; they do not select PHP from the incoming shell path. PHP extension generation/building and native tests use the same installed tool set. A shell inspection of a different system PHP is no evidence for the interpreter used by these targets.

The PHP library requirement stays at `>=8.4` (equivalent to `>=8.4.0`). The development/verification baseline is PHP `8.4.27`; the Windows installation baseline is `8.4.27-1`. Raising the development patch does not raise the minimum supported library version.

Before the phase split, the parity job ran `parity-check` independently of the script-unit job; both installed the locked graph in their own checkout, and `ci-passed` required both. All suite targets still run exactly once. CI uses `var/bootstrap/npm-cache` for setup-node cache discovery, bootstrap and subsequent npm installations; the cache stores downloads, never installed packages or build output, and the package lock remains authoritative. In CI run 40439038565, scripts took 12m23s after a 7m04s queue; script units took 230.7s and parity took 240.1s sequentially. Splitting those targets removes that sequencing; a fresh run must measure the resulting duration and queue separately.

CI 40450000056 at 86edcaa1 passes all workers and ci-passed. It takes 8m06s from the first worker start to aggregation completion, with 8s queue time (8m14s total). Scripts take 5m47s and parity 6m55s independently; showcase is the longest worker at 7m24s. Network and installation times vary between runs, so these measurements establish the observed result rather than a fixed speedup.

CI [40671820218](https://github.com/polyspec/template/actions/runs/40671820218) at c634ec15 passes every worker and ci-passed after language dependency isolation; gates 40671820222 and the updated-graph dependency review 40670361859 also pass. Parity executes 253 bindings twice and passes 5,622 cases. The run takes 10m04s execution and 4s queue (10m08s total); PHP is the longest worker at 9m20s. The scoped dependency steps take 0s for npm-only, 1s for Go/Python and 3s for PHP, while the full tool steps still take 64–69s and the parity dependency step takes 7s. Network/bootstrap and test durations differ between runs, so this does not establish a total speedup. T27.1-9-1 integrates selected tools only after the provider release.

Kit supplies selected pinned tool installation. Native CI workers declare their tools with `make install-tools TOOLS="..."`, then install their own locked package graph. PHP extension workers also use `make kit-install-php-arginfo` and `make kit-install-symbols EXTRACTORS=php`; no installer is copied into template. Mixed script, generation, delimiter and showcase workers retain the complete environment they execute, and the toolchain audit verifies the complete declared tool set. Pages prepares Node only. Installation stays online and checks stay offline.

Kit owns the independent `parity-api-check` and six `parity-bindings-<implementation>-check` targets. The jobs `parity-api` and `parity-bindings` of the kit pipeline `.github/workflows/ci-pipeline.yml`, which the job `kit` of `.github/workflows/ci.yml` calls, run each exactly once, and no other job of `.github/workflows/ci.yml` runs one (T27.1-44, T27.1-43). Template supplies build prerequisites without replacing provider recipes. `config/ci.json` declares the phase mode and native package setup for the synchronized kit pipeline; Kit validates complete coverage, and its parity setup installs the arginfo generator for `packages/php-ext` itself. The default `parity-check` remains available as the complete provider check.

The shared tools come from the locked npm package `@polyspec/kit`. A clean checkout first installs its lock with the exact npm of `packageManager` (`npm exec --package=<packageManager> -- npm ci --ignore-scripts --allow-remote=root`); CI bootstraps the installed package this way before its first make. The Makefile includes `node_modules/@polyspec/kit/scripts/kit/kit-bootstrap.mk`, which selects source tools for a native development link or compiled tools for a packed release, without a sibling checkout. `make install-tools TOOLS=npm` runs that package's bootstrap installer and writes the npm wrappers in `var/tools/bin`; `make install-packages` installs `package-lock.json` with the pinned npm. `make install-tools TOOLS=npm` starts with any node of the machine, installs mise from its release archive, checked by the sha256 of `config/toolchain.json` `mise`, then the node of `mise.toml` with it, and the npm wrappers run npm with that node; every later step runs the node of the checkout (kit K171). `make install` then runs `make install-tools` (`$(KIT)/install-tools.$(KIT_EXT)`), which installs every tool of `mise.toml` with `mise install --locked` at the digests of `mise.lock` into `var/tools/mise`, then the PHP lint of kit; it takes no tool names. `make toolchain-lock` writes `mise.lock` for linux-x64, linux-arm64, macos-arm64 and macos-x64 after a change of `mise.toml`. A recipe never runs the Go or the Python of the machine, and the npm, Go and Python of the machine are not changed. The kit.mk of kit runs every recipe with the environment of mise of the checkout and puts `var/tools/bin` and the shims of mise, `var/tools/mise/shims`, first on `PATH`; the bootstrap writes `var/tools/go.mod`, so the Go sources under `var/tools` are a module of their own that `./...` does not walk (kit K135). The Makefile and exports `GOTOOLCHAIN=local`, so go never downloads another toolchain, and `GOCACHE=var/go/cache`, so go builds into the build cache of the checkout and never into one that other checkouts and runs share. GNU Make 3.81 starts a recipe line without shell syntax itself and finds its program with the `PATH` that make started with, not the exported one, also when `SHELL` names another shell; a recipe therefore starts each tool of the checkout by its absolute path, node as `$(NODE)` and npm as `$(NPM)` of kit.mk and go as `$(GO)`, its shim, and gofmt only in lines with shell syntax, which the shell runs with the exported `PATH`; `make kit-check` fails a recipe that starts a tool of the checkout by its bare name (kit K171). `tests/scripts/toolchain-files.test.mts`, which `make owner-check` runs for every change, fails with the expected and the actual version when Node.js, npm, Go, Rust, the PHP minor version or Composer of the recipes differs from these files. A tool that is missing fails the target that runs it.

PHP is pinned by its minor version: setup-php, which installs PHP in CI, installs the latest patch of a minor version and cannot pin a patch. Each run of `make ci-targets` records the versions it ran on, the PHP patch included, in `record.json` and `summary.md` of its report, which every CI job uploads. Composer is pinned exactly in `mise.toml`, and setup-php installs no tools (`tools: none` in the workflows). make is not pinned: the Makefile uses no construct newer than GNU Make 3.81, and make 3.81 and GNU Make 4.4.1 printed the same commands for every target (T17.1-4). The CI jobs run on `ubuntu-24.04`, pin every action by its commit and install with `make install-tools TOOLS=npm`, `make install-packages` and `make install`; no job sets up a Go or a Python of its own.

The PHP extension `packages/php-ext` is an implementation in C. kit's `make build-php-ext` builds it with phpize, configure and make of the php-config on `PATH`, which must belong to the php on `PATH` that runs the tests, for every PHP version of `config/toolchain.json`; CI installs both with setup-php. `make php-ext-arginfo` generates its arginfo header from the stub with gen_stub.php of the PHP build.

## Commands

```sh
make install
make help
make owner-check
```

`make owner-check` runs the owner checks of the changed paths: the uncommitted changes, the paths of `PATHS`, or the paths changed since `BASE`. `config/owner-checks.json` declares, for globs of paths, the make targets and node test files that own them, and the tests that run for every change (`always`). `inputs` of the same file declares, for each check target, the globs of the paths that it reads, such as `packages/go/**` for `lint-go` and `packages/compiler/**` for `conformance-generated-go`; every path of an input needs a rule that selects the target or a target that runs it as a prerequisite, so a change of the path runs every check that reads it. Before any owner runs, the script fails on a tracked path that no rule owns, on an input path whose rules do not select its target, on a glob that matches no path, on a target that is not in the Makefile and on a target that runs the full suite; each failure names the path, the glob or the target. A rule with `variable` passes its changed paths to its targets: a change under `tests/cases` runs `make conformance-cases CASES="<paths>"`, which runs the AST conformance and the four generated conformance runners for those cases only, while the conformance targets of `make check` run every case.

`make install` runs `make install-tools`, which also installs the Rust toolchain that `rust-toolchain.toml` names with `rustup toolchain install --no-self-update` and changes nothing when it is installed (kit K151), and `make cargo-downloads-fetch`, which downloads the crates of every `Cargo.lock`. The Makefile exports `RUSTUP_AUTO_INSTALL=0`, and the CI workflows set it, so rustup never installs a toolchain on the first cargo: the test files of one `node --test` run start cargo at once, and their concurrent installs broke each other (T18.7-1); a missing toolchain fails with rustup's message `toolchain '...' is not installed`, which names `rustup toolchain install`. The root `package.json` declares the JavaScript packages of `packages/` as npm workspaces and holds the development tools that the root runs, while a package holds those that only it uses, the CodeMirror peers of `packages/codemirror` and vsce of `packages/vscode`, whose script `package:vsix` `make vscode-package` runs; npm links each workspace package into `node_modules` and the commands of the packages into `node_modules/.bin`, where the recipes start TypeScript, tsup, esbuild, Vitest, Playwright, VitePress and vsce (`scripts/tools.mts` for the scripts), so a package reads the build of another package where the build writes it (T24.2). `make install` also runs `pip download --require-hashes` of the python of `mise.toml`, which downloads the build requirements that `packages/python/build-requirements.txt` pins by version and SHA-256 into `var/python/wheelhouse`; the package install check builds the Python wheel offline from that directory.

`make build-ts`, `make template-build-language`, `make template-build-lsp`, `make template-build-codemirror` and `make template-build-vscode` run `scripts/build-package.mts --package <package>`, which builds the package only when the hash of its inputs differs from the one recorded in `packages/<package>/dist.inputs.json`; otherwise it prints that `dist` is current, so one run of the suite builds each package at most once. The inputs are the sources and configuration of the package, its manifest, the root `package-lock.json`, the installed copies of the packages of this repository that it depends on, and the version of Node.js. tsup bundles the modules of a TypeScript package, and the TypeScript compiler writes its declarations (`tsc --emitDeclarationOnly` with `tsconfig.json` and `tsconfig.node.json` for `template-ts`, `tsconfig.build.json` for the other packages) into the same directory, one `.d.ts` per source file under the directories of the sources; the declaration build of tsup calls the JavaScript API of the compiler, which TypeScript 7 does not have. A build writes into `packages/<package>/dist.next-<pid>` and moves each file into `dist` with a rename, a file after the relative modules it imports, so the entries move last; then it removes the files of the previous build that the new one does not have. A reader of `dist`, such as another repository that copies a package or the next target of a run, never finds a file missing. Limit: a reader that reads several files while a build of changed sources publishes can combine files of the two builds, for example an entry of the previous build whose chunk the new build removed; a rebuild of unchanged inputs writes the same files. With `--install`, the npm copy in `node_modules` is installed again only when its files differ from the package, and in the same way: each file that differs is written into `node_modules/<name>.next-<pid>` and moves into the copy with a rename, a file after the relative modules it imports and `package.json` last, then the files that the package no longer has are removed, so a reader of the copy, such as another test file of the same `node --test` run, never finds a file missing. A change of the dependencies of a package is a change of `package-lock.json`: the install then fails and names `npm install` as the fix. `tests/scripts/build-package.test.mts` builds and installs the packages that it depends on itself, so it passes on a checkout where nothing was built.

The full suite, `CHECK_TARGETS`, holds `hooks-check`, `typecheck`, `template-test-compiler-types`, `docs-static-check`, `template-test-scripts`, `editor-boundary-check`, `compiler-interface-check`, `contract-check`, `function-contract-check`, `function-inventory-check`, `benchmark-check`, `template-lint-go-format`, `template-lint-rust-format`, `template-lint-showcase-format`, `template-lint-showcase-warnings`, `template-lint-php-format`, `test-ts`, `template-test-language`, `template-test-lsp`, `template-test-codemirror`, `format-check`, `template-test-vscode`, `template-test-vscode-integration`, `test-go`, `test-rust`, `test-php`, `conformance-ts`, `conformance-go`, `conformance-rust`, `conformance-php`, `conformance-python`, `test-python`, `conformance-generated-ts`, `conformance-generated-go`, `conformance-generated-rust`, `conformance-generated-php`, `conformance-generated-python`, `delimiter-matrix`, `generated-native-check`, `template-test-ext`, `typed-generator-compile-check`, `generated-lint-check`, `template-install-check`, `template-test-browser`, `showcase-check`, `benchmark-smoke` and `docs-verify-idempotent`. The shared gates of kit (`kit-gates`: the static gates, `parity-check` with its phases `parity-api-check` and `parity-bindings-<implementation>-check`, and the lint of each runtime) are not in it: `.github/workflows/ci-pipeline.yml`, which kit gives this repository and the job `kit` of `.github/workflows/ci.yml` calls, runs them once (kit S12, K870, T27.1-43). Every target of the full suite and of its prerequisites runs at most one command: a target with several checks names them as prerequisites, such as `lint-go` and `lint-php` of `lint`, and the Makefile sets `MAKEFLAGS += -k`, so make runs every check after a failed one and fails at the end; a prerequisite that fails keeps the targets that depend on it from running. The scripts that check each language (`scripts/check-generated-*.mjs`, `scripts/check-typed-generator.mts`, `scripts/check-package-installs.mts`) run every language through `checkLanguages` of `scripts/language-checks.mts` and name every language that failed. `tests/scripts/failure-accumulation.test.mts` checks these rules. `lint` runs the lint targets of kit with the configuration that kit copies (T24.6): `lint-ts` runs oxlint with oxlint-tsgolint (`.oxlintrc.json`) and knip (`knip.json`), `lint-go` runs golangci-lint (`.golangci.yml`) and deadcode in each Go module, `lint-rust` runs clippy in each Cargo workspace, `lint-php` runs phpcs (`phpcs.xml.dist`) and PHPStan (`phpstan.dist.neon`), and `lint-python` runs ruff (`ruff.toml`) and vulture. The format checks of template are `template-lint-go-format` (gofmt), `template-lint-rust-format` and `template-lint-showcase-format` (`cargo fmt --check`) and `template-lint-php-format` (Pint); `template-lint-showcase-warnings` compiles the Rust showcase adapter with warnings as errors. `test-rust` and `template-test-ext` run clippy with warnings as errors on the Rust crate and on the PHP extension.

Development runs unit tests only, and no full or end-to-end check runs locally, neither during development nor before a commit or a push: `make owner-check`, the conformance runners, the browser tests and the VS Code integration test do not run locally, and CI runs the full suite. The CI workflow (`.github/workflows/ci.yml`) runs on each push to `main` and on each manual run (`workflow_dispatch`): each job runs its targets with `make ci-targets`, every target of `CHECK_TARGETS` in exactly one job (`tests/scripts/suite-parity.test.mts`), and every job uploads its report of the logs, the failures and the toolchain versions (`var/report`).

Every make invocation sets `core.hooksPath` to `.githooks`, the tracked hooks of `config/checklist.json`; `make hooks` sets it, writes the hooks and checks them, and `make hooks-check` fails while `core.hooksPath` is not `.githooks` or a hook is missing, not executable or changed. A push is not checked: the message rules run at commit, and the CI run of a commit is read at release.

Version 0.x works on `main` directly (AGENTS): there is no pull request, merge queue or GitHub ruleset. A checklist row becomes `[o]` when its owning unit test passes, and `main` is pushed once, when every row is `[o]`. The run of `.github/workflows/ci.yml` on that push is the evidence of the commit: its last job `ci-passed` needs every other job of the workflow, runs after each of them also when one failed, was skipped or was cancelled (<code v-pre>if: ${{ always() }}</code>) and runs <code v-pre>make ci-passed RESULTS='${{ toJSON(needs) }}'</code> (`node_modules/@polyspec/kit/scripts/kit/ci-passed.mts`), which prints the result of every needed job and fails unless each one is `success`; its step has no condition of its own, because a skipped step would pass the check. A job added to `ci.yml` is listed in `needs`, and `tests/scripts/toolchain-files.test.mts` fails when `ci-passed` is missing, is not the last job, lacks <code v-pre>if: ${{ always() }}</code>, does not need every other job, runs on another runner or runs another step (T22.1-3). A newer push does not cancel the run of an earlier push. The workflow `.github/workflows/pages.yml` publishes the documentation site of every push to `main`, and also on a manual run (`workflow_dispatch`); and `.github/workflows/release.yml` runs only when the maintainer dispatches it with the id of a successful run of `ci.yml` and a version, and releases the commit of that run (`docs/operations/publication.md`).

`test-go`, `test-rust`, `test-php` and `template-test-ext` run `go test`, `cargo test` and PHPUnit through `node_modules/@polyspec/kit/scripts/kit/run-tests.mts`, `template-test-ext` with `--php-extension`, which loads the built extension into the PHP of PHPUnit; `test-ts`, `template-test-language`, `template-test-lsp` and `template-test-codemirror` run vitest and `template-test-vscode` runs `node --test` through it. The runner prints each test when it starts, every 5 s while it runs and when it passes, fails or is skipped, with its elapsed time, and stops the tool when a test outlives its own timeout (30 s, `--timeout <seconds>`); no package, file or whole run has a time limit. `cargo test` runs one test at a time, so each test prints its start before its result. PHPUnit also stops a test after 10 s (`enforceTimeLimit`, `failOnRisky`). A Go package that does not build prints its compiler output and `✖ build of <package> failed`, and the summary line names the compiler errors. A run in which no test ran fails with `no test ran`; a test does not skip itself when what it needs is not built, it builds it, and the conformance runners run every language unless `--langs` names them, failing on an absent package. `template-test-scripts` runs the tests of the runner in `tests/scripts/`.

## Change procedure

1. Change the specification in `docs/spec/` and its `.ko.md` file.
2. Add or change the fixture cases in `tests/cases/` and the expression fixtures in `tests/fixtures/expr/`.
3. Add a failing test in the package, change the code, and keep the test.
4. Update `docs/features.md`, `docs/features.ko.md`, `CHANGELOG.md` and `CHANGELOG.ko.md`.
5. Run the Red and Green tests that own the change and `make docs-check`.
6. Commit with a message that names the action, the subject and the object.

Each implementation binding of `config/parity.json` uses either a scalar `symbol` or a nonempty unique `symbols` list. A list names the exact publication points of the same verified contract, such as an engine type, its constructor and its owned program. Lists use no prefix or wildcard expansion. The declaration gate rejects invalid bindings and the native SDK consumer units verify every listed name. Existing operation/field units still assert their canonical publication points from `packages/compiler/interface.json`.

The shared provider gate declares Python in `config/ci.json` under `tools.shared`: test-marker validation parses Python source. The shared static checks need it independently of native runtime workers.
